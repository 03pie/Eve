## 架构边界

完整 ReplacementOperation 必须共同拥有模块预约、Core 闭包作用域、旧/新不可变定义、旧配置和目标修订。上层协调依赖 Module、ConfigKernel 和 Session，Core 不反向依赖这些策略层。新代使用独立 RuntimeId/InstanceId，不能改写旧 Runtime 的工厂。

先沿用同一服务索引和 PublicationControl 实现候选授权。授权绑定唯一作用域的当前发布视图，跨排队激活和子实例继承，不引入全局开关、线程局部绕过或第二套资源索引。只有旧闭包真实静止后才能创建候选；普通挂载、更新、停止和手动服务入口继续检查占用。候选组外不可见，丢弃复用既有发布组放弃、实例停止和清理屏障，失败保留所有权。

新顶层工厂的 RuntimeId 参加占用；恢复的原消费者依完整服务键隔离，动态子实例沿用父视图和实际输出占用，不能因为共享同一个消费者 Runtime 就锁住其他 realm。新增成员在任何调度/插件回调之前纳入作用域和 Kernel/父代所有权。旧 stop 回执与候选 discard 回执分开，旧静止不表示候选清理成功。

## 早期实施记录（历史）

### 上层集成的职责与提交顺序

1. 完整操作位于依赖 Module、ConfigKernel、Session 的宿主协调层。KernelDriver 继续独占条目运行账目，Coordinator 独占目标修订，Store 独占保存账目；不向外开放可分别调用的 setDefinitions 或可变记录表。
2. 新完整定义通过 `ConfigurationDefinitions::replacing` 构造。未改插件共享同一不可变节点，只替换明确列出的已知插件；新目录取得独立校验身份，合并后重新检查模块别名。此操作不注册 Runtime、不切换驱动、不接受配置。候选只持身份标记，不能靠旧草稿延长旧工厂寿命。
3. 长时间停止、创建和就绪等待期间保留模块预约与 Core 作用域；无关目标继续使用原有接受机制。最终在协调器已无在途/待执行工作时，从最新目标重新合并受影响条目并检查冻结版本，而非覆盖操作开始时捕获的全目标。
4. Session 的同步访问门禁保护最终准备窗口。先验证并分配新目标、Driver 的受影响记录和新的观察回调，再取得 Module/Core 准备凭据。持模块目录锁期间不能执行 schema、availability、调度器或插件回调；准备失败不改变任何当前目录和目标。
5. 成功临界区共同发布 Core 服务/规范定义、Module 角色，以及已准备的 Driver/Coordinator/Store 元数据。旧值移到操作持有的退役对象，避免交换时在锁内析构最后一个业务捕获。退出模块锁，释放模块预约，最后才调用 Core release 通知。现有两层准备凭据尚未实现后三项 Loader/Session 交换，不能宣称完整原子提交。
6. 记录替换以真实 InstanceId 区分新旧实例，复用 Driver 已有观察者的实例身份校验。配置子实例按条目映射由真实父代重建；未登记的临时子工厂仍归拥有者，不复制出来单独重放。

### 目标账目准备增量（11 月 3 日）

`target_commit_p.hpp` 是 Loader 私有的同步准备凭据，不增加公开的接受目标或切换目录接口。Coordinator 和 Store 的控制块仍分别留在原实现文件，跨层准备由小型宿主适配连接，不为访问字段拆出整套控制块或复制状态表。两个公开 facade 仅增加内部友元，布局及公开方法保持。

准备核对相同调度器、同一个已接受目标对象、相同当前修订，以及 Coordinator 无在途/待执行工作；只在最终同步窗口暂时关闭新的业务写入。第二个账目准备失败或重入关闭时，已取得的第一个准备槽自动撤销并恢复关闭泵送，不留下半组占用。凭据只在 owner 线程同步使用，不能跨线程析构或持有它排队等待。

发布只交换预先准备的共享目标并推进两个修订；旧目标保留在准备槽内，Store 变为 dirty，历史 persisted/基线/排队写入不改写。旧保存完成仍只记录旧修订，不能把新目标标为已保存。发布不调用调度器、驱动、schema 或写后端，不完成计划 Promise。上层必须在 ready 检查后无回调地完成 Core/Module 和这些槽的发布，再统一处理 Session 的最终结果及通知；当前尚未接通完整链路。

五项组件测试覆盖共同发布及重复发布、准备撤销/来源或调度器不一致、在途动作/待执行目标拒绝、关闭重入、旧保存晚到，以及发布窗口没有调度器/驱动/写后端调用。测试驱动和写后端为受控替身，不能用它们代替真实 DLL、运行实例映射、磁盘事务或整个 ReplacementOperation 的验收。

### Driver / Session 联合元数据准备（11 月 3 日，进行中）

本轮补齐完整操作最终提交窗口所需的 Loader 私有桥接，尚未提供完整 ReplacementOperation。`Cordis::ConfigReplacement` 组合 ConfigKernel 与 ConfigSession；泛型 Session 的准备槽独立于具体 KernelDriver 和 Module，Core 不向上依赖 Loader。原控制块继续拥有各自账目，公开 SDK 仅增加内部友元，不增加分别切换定义、实例或目标的公开入口。

Core 只向宿主准备桥提供同一 Kernel 的真实 Prepared 成员、配置、realm、附加依赖、父实例和 epoch；映射里的编号只用于关联，不能作为实例来源证明。每次准备产生独立身份，丢弃后重新准备不能复用旧凭据。Driver 核对不可变定义变化与 Core Runtime 换代一致，仅预构造受影响条目；无关条目的身份、输入和账目保留。候选实际父子关系必须对应配置树，沿用实例身份校验的 epoch 观察器，并避免重试准备产生重复观察链。

联合准备先封闭 Session 的同步访问，再验证 Driver/候选与预注册观察器；所有可回调、可分配工作在 Module 锁外完成。最终顺序为：准备 Loader 凭据 → 准备 Module/Core 凭据 → 再核对 Loader ready → 发布 Core/模块角色 → 无回调交换 Driver、Coordinator、Store、Session 元数据 → 销毁模块凭据并解除预约 → Core release 通知 → Loader finish。宿主操作必须在 owner 线程保留 Kernel/Scope 到 finish，不能持准备凭据排队等待。

成功换代推进目标修订并使 Store dirty；旧代重建只接纳原定义和同一个已接受目标对象，保留目标修订、persisted、dirty 以及原历史计划。计划结果在解除门禁后完成；通知失败报告 Failed，同时保留实际提交事实。放弃未完成的凭据报告取消，不默认为 Applied。

### 冻结前拥有者识别的前置修正（11 月 3 日，进行中）

上层预检不能仅用 Driver 的路径→InstanceId 表区分配置实例与手动实例：同一 Kernel 允许多个驱动，未知条目也可能属于另一驱动，不能将查表未命中的实例直接当作手动实例。本轮在真实 InstanceControl 保存宿主私有的拥有者身份。每个 Driver 只有一个无回调的身份对象；实例持有它不会保留驱动、schema 或模块工厂，不建立旁路实例索引。

Driver 的根实例沿原 Kernel 挂载路径在激活前写入身份，Context.inject 的真实子实例继承，普通 remount 保留原身份。手动挂载保留空身份；另一驱动拥有不同身份，即使其会话/驱动已释放，仍被持有的实例也不会丢失原归属。标记不授予 Kernel、模块来源或替换权限；完整操作仍须核对实际闭包和对应驱动的条目记录，不能只凭标记接纳条目。

候选接纳只准备已冻结的真实 Prepared 子树，拒绝覆盖其他拥有者，准备期不写入标记。Loader ready 同时重验标记；在 Core/模块提交成功后的无回调窗口，与 Driver 映射一起接纳候选及其子树。失败撤销继续保留原拥有关系，未配置的手动消费者不因同次替换而被 Driver 收养。

新增拥有者检查覆盖手动/配置实例、两驱动区分、子实例继承、激活前可见、普通 remount、错误线程、非 Prepared 接纳拒绝及身份寿命；已有真实联合提交与树恢复补验新实例的实际归属。最终断言及示例重建后的 Release/ASan 相关回归各 80/80，GCC 相关目标专项 54/54，日志 build/p5-m2c5-owner-current-{release,asan,gcc}-*；两个编译器各六个公开头独立编译、24 项 C++ 格式、31 项源码/构建/文档哈希及十一项实际 ASan 当前对象核对通过。该修正提供可靠分类依据，尚未实现完整操作的冻结前拥有者预检或重建协议，M2c5 继续。

### 冻结前重建输入与参与者匹配（11 月 3 日，进行中）

沿同一 Core 作用域读取实际旧句柄和占用时捕获的输入，要求同 Kernel、Reserved 状态及完整暂存定义。原输入的读取和来源重验移到 `replacement_inspect.cpp`，准备/发布继续在 `replacement_commit.cpp`，不把 Loader 策略放进 Core。

Driver 的私有检查按实际记录核对旧 Runtime、父实例、配置、完整 realm 和附加依赖，构造新目录下的配置重建输入；复用既有类型契约合并和提供者排序，并让排序读取明确提供的新目录。不可变节点换代核对与最终提交共用同一实现。无关条目的身份、配置或有效契约变化、未知 realm、依赖预算以及不兼容的已配置提供者在冻结前拒绝。可重入 availability 后再次检查目录、目标、关闭及作用域状态，不登记目标、不启停或保存实例。

Driver 只报告自身条目以及实际手动根、拥有者子实例和外部拥有者。独立的 `configuration_reconstruction.cpp` 组合显式提供的多个驱动，对完整闭包逐项检查归属覆盖；遗漏驱动时拒绝，提供两个实际驱动时可共同覆盖跨驱动消费者。参与者重复或缺失也拒绝，不按“在当前驱动查不到”就推断为手动实例。无活动条目的完整定义目录也可参加，不能假设初始空目标已经执行过 Driver 动作或拥有 currentTarget。

`OwnerManagedChild` 明确保留拥有者重建义务，即使子 Runtime 恰好已登记，也不将其当作可单独重放的工厂。当前输入检查不授予冻结/停止权限；纯 current 只重验来源和准备期状态，实际闭包、epoch、修订与健康仍由 Core freeze 重新核对。完整操作还须解决拥有者义务、Session 配对、模块来源/兼容性、全局新图和受影响目标重合并，再开始破坏性动作。

新增五项检查覆盖真实手动消费者/子树、两个配置驱动、配置父子树、无关目标变化、来源或 Kernel 不符、availability 解除作用域重入、类型不兼容及空配置/重复参与者。测试中的驱动复制假设被现有已删除复制构造函数拒绝，已撤回，不计为产品缺陷或红测试。首轮四项新增场景后 Release/ASan 相关回归各 84/84；追加空配置检查及最终源码/真实模块产物重建后的 Release/ASan 相关回归各 85/85（build/p5-m2c5-preflight-verified-{release,asan}-*），GCC 相关目标专项 59/59（build/p5-m2c5-preflight-current-gcc-*）。27 项修改区域格式、35 项源码/构建/文档哈希与十三项实际 ASan 当前对象通过；六个公开头源码哈希与前轮两个编译器各六项独立编译检查一致，本轮未改公开声明或重跑该头检查。本轮仍是 M2c5 集成增量，未提交，不进入 M3。

### 逻辑配置条目与真实拥有单元（11 月 4 日，进行中）

原操作只从实际目标 Runtime 的活动图取得闭包，已停止的配置子项仍留在 Driver 账目，却不再存在于 Core 活动图。因此它的活动祖先可能未被占用；另一个问题是原提交映射把“旧实际重建输入”与“旧配置记录 ID”视为同一来源，无法接纳已销毁记录。不能伪造旧实例，也不能靠把祖先 Runtime 当作换代目标来扩大占用到所有同类实例。

Driver 的私有 reconstructionOwners 只从原拥有记录找缺少实际实例的目标条目及最近活动祖先。Core 私有 reserve 沿唯一 Kernel 图验证祖先选择，再复用现有父子/实际消费者/等待声明闭包、冲突检查和原子占用；目标 Runtime 集合保持原样，祖先选择留在私有 Selection 中供 freeze 重算。跨 Kernel 编号拒绝，重复祖先去重，不新增公开权限入口或旁路实例表。

配置预检和最终准备共用 reconstructionPaths，目标子项尚无实例时，其配置祖先仍在共同重建范围内。宿主 ConfiguredSource 合并路径、参与者与旧记录 ID，替代原先的并行数组和无效索引哨兵。Core 实际旧输入继续用于真实拥有单元及报告，已停止记录 ID 只用于 Driver 映射核对；逻辑条目不冒充 Core 实际成员。所有元数据仍沿原同步准备/发布/通知协议提交。

真实两后端新增三种场景：活动祖先下业务子项已停止后成功换代；候选激活失败后的旧配置重建；祖先也停止、Core 无活动目标成员时，完整配置树重建并实际写盘。测试布置先用真实 Core 凭据取得实际子句柄并停止，不按编号构造实例；之后完全通过公开 ReplacementOperation 执行。新增 Core 检查验证祖先包含真实子树与消费者、重复选择、跨 Kernel 拒绝、占用冲突和 freeze 仍按同一祖先重算。

已有相关回归 Release/ASan 各 123/123；之后追加祖先也停止的场景，两配置当前新增专项各 7/7。具体日志、GCC 与最终源码检查见 [复查](code-review.md#p5-m2c5-逻辑条目与祖先占用复查)。未证明从未创建的逻辑子项、逻辑祖先定义并发换代或全部故障组合；这些仍须在阶段最终矩阵验证，当前未提交、不进入 M3。
