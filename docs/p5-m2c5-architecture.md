# M2c5 架构复查与结构收敛方案

日期：2026-11-04。先设计、再修改；本轮不扩大 P5 功能范围，M2c5 出口不变。

## 问题和边界

### 低层原生服务故障的收口审计（2026-11-05，待实测）

整阶段审计发现 inputSources 只提取 Core 托管提供者及祖先；低层 NativeModule.create 发布的真实 NativeServiceEndpoint 不属于该树。正常 service/effect/实例/模块撤回已有 Core 读门禁，但 native quarantine 只封闭原生入口并记录模块错误，不能据此证明实际 Core 绑定已失效或悬挂拥有者已收到中断。

先用现有 services C ABI 夹具发布真实外部服务，native/Qt 主目标以附加依赖消费，进入真实 ReplacementOperation 的悬挂拥有者阶段；夹具让同步回执返回非法 PENDING，沿已有请求协议产生实际 quarantine。检查来源已 uncertain 后操作结算、旧代恢复因真实输入失效而失败及资源保留，不人工修改 Core 绑定或模块来源字段。夹具路径由该测试显式环境参数提供并加入构建依赖，不影响生产环境或其他测试入口。

若复现，优先审查原生故障如何使原 Core 服务账目失效，而不是从裸实例编号推断代次、另建来源索引或把无法保证的服务静默排除出支持范围。只在证明现有机制无法承载后调整边界。

真实两后端均复现 0/2（raw-source-red-*），提供者已经 uncertain，而 operation.settled 仍未就绪。采用现有 Module 来源故障通知修复：Core 私有 SPI 返回已封存、未托管输入的真实对象/类型/提供者及阶段用途；宿主从实际 NativeServiceEndpoint 的原所有者取得 generation/instance/epoch，不调用业务代码。托管来源同样由宿主将 Core 真实拥有视图转换成 Module 输入来源；Module 在原 instanceOrigins 核对托管属性、实际身份及可选 Runtime，合入原 borrowed/readers，不建立裸编号→模块推断表。

由 Cordis::Replacement 明确依赖原生宿主适配，ModuleNative 不再读取 Core 私有拥有视图；Core 仍不知道 NativeServiceEndpoint 或模块策略。未托管来源没有 Runtime，用空 optional 表达，不伪造 RuntimeId。真实模块读持有保护其代次，先前的短期故障事件可在 owner/worker 来源故障时复用原投递失败门禁；不用只在 owner 退役绑定的补丁掩盖来源权限缺失。Core 绑定仍保留真实原生资源所有权，quarantine 不等于释放 DLL 对象。

### 模块来源故障与悬挂拥有者的验证设计（2026-11-05，实施前）

Core 绑定读意图已有退役通知，Module 的 GenerationFailureSignal 当前只保存实际业务错误，最终准备会检查错误；这不能直接证明拥有者永不返回时也能结束操作。先用已有 peer 真实 C ABI DLL 和已封存的候选独有来源验证：拥有者进入候选重建后悬挂，另一真实低层 create 返回错误却留下原生句柄，沿原协议检查置该代次失败。使用独立且合法的低层实例编号，不伪造 Core 成员或模块错误字段。

该 peer 不属于旧树或恢复计划，故目标应丢弃候选、完整恢复旧树并释放本次权限；真实故障 peer 自身仍按原 quarantine 保留，不把外部模块的不确定资源记成已清理。检查调度屏障后操作能结算、来源故障原因、完整旧成员/角色，以及晚到拥有者结果不改变结论。不以人工取消来冒充来源故障中断。

若复现缺口，再在原唯一代次故障信号上提供一次性通知，并沿已封存的实际候选/恢复来源观察；不轮询、不新增全局代次/订阅目录、不让 Core 反向依赖 Module。异步通知必须在目录/代次/信号锁外交付，普通最终健康检查和失败保留语义仍需保留。实现取舍须在复现后再具体确定。

真实两后端已在调度屏障后的 settled.isReady 断言复现 0/2（source-loss-red-*），不是超时或人工取消。实施方案：保留 GenerationFailureSignal.error 为唯一代次错误；native/Qt 两个实际故障写入入口收敛到同一通知适配。沿原 catalog.replacements 扫描目标当前/候选及 borrowed.required/original，候选/恢复各通知一次；来源用途判定与最终提交健康检查共用私有谓词。

通知 Promise 由实际宿主 Execution 持有，原预约仅保存弱事件槽。释放预约不销毁宿主通知生产者，避免纯解除权限路径意外执行 BrokenPromise 观察者；操作终结后随 Execution 释放，故障目录不持有 scheduler、Kernel 或工厂。禁止直接给永久驻留代次挂不可撤销的 Task 观察链，否则每次成功替换也会保留观察者。通知收集使用实际目录，锁外完成 Promise；宿主复用现有弱中断/owner 串行门禁，并在冻结前及进入每次构建时检查实际阶段来源，覆盖故障发生在 Prepared/Stopping/Discarding 的时序。最终准备的原有健康锁与检查保留。

候选独有来源修复及相邻场景 Release/ASan 各 40/40。接着用同一真实夹具验证另一用途：peer 成为现有内置服务提供者的真实 Native 祖先，故候选和恢复都依赖该代次；同样故障必须阻止旧代重建并报告 RecoveryFailed、保留实际预约和空映射，不能沿候选独有来源的成功恢复分支处理。复用已有失败保留测试的宿主退出分支，不开放生产清理绕过接口。

### 多参与者最终准备撤销的验证设计（2026-11-05，实施前）

现有完整操作的双会话成功及候选启动失败，不能证明部分最终元数据准备后的异常撤销。职责保持不变：每个 ConfigurationCommitControl 用 RAII 持有自己的 Driver/Session 准备槽，宿主 commit 组合这些凭据，发布前失败必须释放全部槽；Core/Module 不增加多会话策略或测试开关。

复用真实两版本 DLL 与现有双会话整体操作夹具，在 begin 完成后安排 schema 回调：第一个参与者校验后，第二个参与者校验时，直接检查第一会话诊断已因实际准备槽而拒绝、第二会话仍可诊断，且目录角色与磁盘均未发布。分别让第二次校验抛错和调用真实 operation.cancel；不以校验计数本身冒充已取得准备槽。

出口要求完整旧代重建、两个会话原修订及 persisted/dirty 保留、无候选映射混入、角色及预约释放、准备槽不残留且两会话重新可保存/关闭。失败和取消分别报告 Restored 与 Cancelled（recovered=true）。先在现有支持矩阵构建结束后实施，避免编译期间修改输入；若验证通过则只增加缺失证据，不为增加代码而改动生产状态机。

### 原生撤回准入的审计要求（2026-11-05，待真实 ABI 回归）

真实 service_withdraw/effect_close 已复现健康实例被置为 Failed（修复前 0/2）。调用方审计还确认 NativeInstance.close/NativeModule.close 经 cancelBusiness/retireAll 到达同一失败路径；四个主动入口应共用 NativeServices 对实际绑定的只读准入，而不是分别处理 quarantine 后果。实例与模块关闭必须在 closing、原生状态或模块 Draining 发布之前拒绝；Module 生命周期准入与原线程/所有权/重复关闭语义保留，Core 检查在目录/实例/模块互斥锁外执行。

Core 原绑定读检查移到已有 service 私有声明供桥复用，保留真正退役入口；ABI 状态转换映射由 service 和 resource 两个实际入口共用原实现。服务撤回检查单项，effect/实例/模块关闭先检查全部实际服务，失败不落半组请求或状态；已 Retiring/Released 仅允许幂等继续清理。低层原生实例仍用自己的真实句柄和服务绑定，不从宿主填写的实例编号推测托管身份。正常解除权限后须能沿同一原关闭/撤回路径完成。

新增读门禁使 ProviderHandle.retire 可以正常返回 ConfigConflict；调用方不能继续假设任何退役失败都是资源故障。审计发现 NativeServices.retire 先设置 withdrawing，再对 Core 拒绝执行 quarantine；NativeResources.withdraw 也先登记请求/撤回标志再启动 retireEffect。持有读意图时的普通插件 service_withdraw/effect_close 必须作为无副作用的 BUSY 准入拒绝，不能因此把健康业务隔离成 Failed。

修正前须用现有 resource_fixture 的真实 C ABI 注册/撤回入口和实际 Core 输入封存复现。准入应直接检查 NativeBinding 持有的实际 Core 绑定，在请求分配及撤回标志、effect 状态变化之前完成；effect 关闭须先检查全部所含服务，不能只关闭半组。不复制替换读者算法或按 CordisHandle 猜测 Core 权限，优先复用 Core 原绑定读检查。已经真实退役的重复清理继续幂等；不可避免的实例/模块故障清理与主动请求的权限分开沿真实生命周期处理，不通过任意布尔参数授予调用者绕过权。

验证须核对 BUSY、零 request、服务仍可调用、实例/模块不被 quarantine、无新请求/资源残留，解除读权限后真实撤回可完成，以及原正常 effect/实例清理路径。Module 实际来源、动态声明封存及组合故障仍须继续；本节不把源码推断计为已复现或已修复。

### Module 来源权限的实施设计（2026-11-05，下一增量）

实施细化：Module SDK 提供不含 RuntimeId 的 ModuleFactorySource（真实代次、插件定位值）；ReplacementConstruction 与动态描述附可空来源，空值明确表示内置工厂。平台在拥有者预检前从实际工厂/旧来源及本次实际换代导出默认值，拥有者复制或明确改变动态来源；恢复旧成员必须保留实际旧来源。Service 计划仍只处理契约，来源默认与恢复保真归宿主独立 sources 实现，Module 不反向依赖宿主 SDK。

原 reservation 用不可变计划的唯一指针封存两阶段 generation→plugin 集合，空/非空表达模式，不加另一状态标志；源代次健康、已协商业务接口、插件目录、目标前驱/角色及非目标 Current 核对通过后，新的代次持有与原读者索引和纯计划一起交换。admitGeneration 先按实际 Context/runtimeOrigins 检查集合及真实持有，再进入 create；retainBorrowed 只在原未封存模式动态扩展。Prepared 将实际来源与各成员声明比较，允许新 RuntimeId；空来源也必须确实为内置工厂，不能靠全局允许集合掩盖成员错配。

真实回归先验证“peer 已作为服务来源被读持有，但未声明可创建其插件”仍执行 create 的缺口，修复前 0/2；C DLL 导出独立 create 调用计数，不用最后存活实例数冒充未执行。再补正确声明、错误插件/角色、错误实际来源及逐成员错配，分别验证冻结前拒绝、创建前拒绝和实际兑现拒绝，不能混用三类证据。

Core 绑定读意图保护真实服务对象，但不能代替 DLL 代次读意图。当前 Module.borrow 仅识别规范工厂；catalog.retainBorrowed 仍在实际创建时扩大使用集合，尚不能证明预检已冻结全部可执行来源。后续须把实际外部提供者和动态未来工厂来源一起接入原 borrowed/readers，并在完整计划完成后封存准入；低层未封存用法保留原动态语义，明确兼容原因，不新建代次目录。

实际外部提供者来源必须从同 Kernel 的真实 Scope.readBindings 取得，核对实际提供者与祖先的实例/epoch/runtime，再由 Module 唯一 instanceOrigins/runtimeOrigins 匹配；不能用调用者填写的 InstanceId/RuntimeId 授权，也不能只查顶层 Kernel.findInstance。selectReplacement 已有完整拥有树遍历，实施时先把这份遍历收敛为 Core 内部实际拥有视图，由闭包选择和读来源适配共同调用，删除原平行 owned/handles/blocked 填充，避免复制第二套遍历或持久运行图。临时子工厂仍不捕获或对外重放。

动态未来声明需要可验证的纯代次/插件定位值，不能伪造一个带空 RuntimeId 的 ModuleRuntimeOrigin。已知工厂来源取实际 Runtime，已有动态成员可从真实旧来源及明确换代工厂导出默认候选/恢复来源；新增或改变来源必须明确描述。定位值经当前 ModuleCatalog、实际角色/前驱/插件、健康/准入/ledger 与排他占用检查后，才合入原 borrowed/readers。非目标模块只接纳真实当前代，不能默默允许别人的候选代；恢复保留原真实来源。新建 Runtime 可有新的 RuntimeId，最终按实际代次/插件核对，不为测试方便要求重放临时工厂或相同 RuntimeId。

实现检查发现 MSVC 的 map 移动可能为哨兵分配，optional 从空交换为有值不能保证不抛出；改为锁前构造不可变计划，最终只交换 unique_ptr，并保留不抛出静态断言。不能删除断言后继续发布半组权限。

来源集合须区分“持有模块生命周期读意图”和“允许本操作创建哪些插件”。外部提供者被读取，不表示拥有者可以创建该模块中的任意插件。完整候选/恢复构造计划的代次/插件纯集合应归原实际 reservation 持有，以空/非空的不可变计划指针表达模式；borrowed/readers 继续证明真实代次持有，不复制另一份目录或用只读持有冒充创建授权。admitGeneration 从实际 Context 的 Runtime 来源核对阶段集合，在执行 create 前拒绝未声明的新来源；Prepared 再逐成员核对实际代次/插件，处理已获全局权限但被放到错误成员的情况。低层未封存协调的动态使用保持原兼容语义，不能因此放宽完整宿主事务。

完整宿主计划封存后，Module.admitGeneration 在执行 create 前必须要求目标代授权或原已声明的阶段读权限，禁止 retainBorrowed 自动增加未声明来源；公开低层未封存协调仍沿原机制。候选 required 与恢复 original 继续分开，最终 Prepared 使用真实工厂来源兑现每项计划。分配和来源检查先完成，原锁内只交换账目，不执行 Core/插件回调；释放继续使用原预约。

验证覆盖：真实外部业务 DLL 提供者及内置子提供者的模块祖先，预检后另一模块预约/close/drain 拒绝及操作后释放；新动态工厂正确声明、错误代次/插件/角色、漏声明创建前拒绝；候选独有代次失败后旧代恢复；原低层动态兼容。Core 原始服务和 Module 实际业务引用分别核对，不以双方任何一个计数代替另一个。该节是实施方案，不是已实现或已验收的声明。

### 外部绑定读意图的实施设计（2026-11-05）

全局求解取得的外部提供者目前只是快照，主动停止/更新和另一替换仍能使预检成功后的来源消失。事务读意图不是实例 committed 调用租约：不得伪造消费者实例或污染实际依赖图。继续复用注册表 replacements 与 Scope 所有权：Scope 保存实际 BindingControl 和候选/恢复用途，跨 Scope 的主动变更检查扫描原操作目录，不新增全局读者索引。只有实际 Published、非故障、非写占用绑定可取得读意图；纯 BindingId 只用于重验同 Kernel 的实际来源，不凭编号授权。

预检全局求解同时返回所使用的实际外部键/BindingId；候选和恢复分别收集。将原输出封存入口收敛为一次完整计划封存：输入检查、输出检查及所需容器分配完成后才一起交换权限，继续使用一个 planSealed 模式和原释放路径，不叠加独立输入封存状态机。不同事务可共享同一绑定的读意图；主动 ProviderHandle.retire、实例 stop/update（包括拥有该提供者的祖先）及另一 Scope 占用实际提供者前须拒绝，并报告真实读操作编号。非破坏性读取和新消费者不受阻。

实际绑定对象的生命周期仍由原提供者及 committed/call 屏障证明。主动退役被读权限阻止；不可避免的实例故障/Kernel 关闭通过仅 InstanceControl 可调用的私有退役入口继续清理，不用事务读意图增加 committed 计数造成关闭互等。该入口与普通退役共用唯一状态转换，在实际 Retiring 后发出候选/恢复各自的来源失效信号；释放不凭强指针冒充有效来源。真实消费者仍按原租约等待，计划本身从不调用服务对象。

候选/恢复来源分开验证；候选独有来源故障不能禁止不需要它的旧代恢复。Core 冻结、构建权限、Prepared/current 及最终纯提交门禁须读取所需实际绑定身份/状态；宿主复用原弱中断观察器打断 Building/Recovering 中未兑现的拥有者任务。Stopping/Discarding 继续等真实清理，后续图验证处理来源变化；Kernel 关闭优先沿原关闭结果结算。读权限在原 removeClaims 解除，不允许因失败预检遗留占用，也不提前解除失败保留操作。

验证先用真实 native/Qt 替换与外部提供者复现主动变更缺口，再覆盖共享读取、祖先保护、取消后释放、故障撤回及挂起拥有者中断、候选独有依赖失效后的旧树恢复和 Kernel 关闭。Core 检查补真实 BindingId/错误线程/失败原子性与低层动态兼容；Module 可执行来源保护继续由其原代次读意图负责，不以 Core 绑定指针替代 DLL 生命周期权限。

### 恢复计划保真检查（2026-11-05，实施前设计）

现有 planConstruction 会用拥有者描述覆盖不透明动态成员的 config、realms 和契约，即使正在构造恢复计划；Prepared 又只比较该计划，可能把已经改变原输入的树报告为 Restored。Core 捕获的 ReplacementConstruction.previous 已持有真实原配置、RealmMap 和有效依赖/输出纯值，无需保留临时工厂或另建恢复快照。

检查放在唯一计划规范化入口：恢复阶段、已有 previous 的动态成员，配置和域映射必须等于真实旧输入，规范化契约必须经现有 serviceContract/sameContract 与原有效契约相等，冻结停止前以 ConfigConflict 拒绝。候选仍可声明未来变化，新增恢复子节点没有旧成员可比较，继续沿原完整声明、全局求解和实际兑现检查接纳，不一律禁止形状扩展。已知工厂与配置项继续使用平台取得的旧输入，拥有者原有禁止覆盖规范工厂的规则不变。

验证通过真实 native/Qt 模块及动态子树，分别改变恢复配置、已知域、有效依赖、输出；每项必须在 rebuild 前拒绝且原三成员保持 Active，模块预约解除。正向检查等价重复依赖规范化后仍可执行完整失败恢复。复用原测试拥有者和清理路径；不为此增加公共接口、第二套比较器或模拟实例编号。

当前依赖方向合理：宿主 Replacement 组合 Module、Core Scope 和 ConfigReplacement；ConfigReplacement 组合 Driver/Session；Session 继续拥有 Coordinator/Store 的业务入口。Core 不依赖 Loader、Module 或宿主拥有者接口。实际实例、模块代次、执行记录和接受/保存目标仍分别由原控制块持有，不应再建一套持久运行索引。

需要收敛的是预检结果的寿命和推进逻辑。ConfigurationWork 当前跨停止/创建阶段保留完整候选与恢复 DriverReconstructionPlan；恢复计划只在预检内使用，而最终目录重合并只需要旧目录、新目录和变更插件集合。完整计划还携带重复的 Core 输入、拥有者分类和条目工厂。默认/自定义拥有者完成回执又复制了一段相同的成员接纳和计数推进逻辑，buildDefault 有未使用的序号参数。

## 本轮实施设计

1. Loader 私有 DriverDefinitionChange 明确组合旧目录、新目录和变更插件集合。DriverReconstructionPlan 在预检期持有它以及真实输入、条目/拥有者检查证据；目录重合并只接收 DriverDefinitionChange，不能依赖整套历史执行计划。
2. 宿主 ConfigurationWork 只保留 DriverDefinitionChange、原接受目标和受影响路径。完整候选计划留在 preflight 局部直到拥有者回调后的 current 重验；恢复计划只用于生成恢复构造输入，离开预检即释放。执行期恢复构造计划仍必须保留，不能误删失败重建所需原工厂/输入。
3. 接纳拥有者结果、核对成员、递减待完成数量和推进 built 归到唯一接纳方法。默认/自定义拥有者共用这条路径；异步回执仍沿 watch 的阶段序号和 owner 串行门禁检查，不重复保存或传递未使用的序号。
4. 删除失效的 numeric_limits 引入和未使用参数。已撤回的 contracts 原型无实际调用链，继续删除，不保留备用实现。

保留 recovery 模式字段：Discarding 阶段仍需区分候选清理与恢复清理，不能仅从展示 phase 推断。保留 OperationDelivery：工作线程只能封闭原子准入和任务，不应读写 owner 状态。保留 Core/Module/配置各自准备凭据：它们对应不同资源权限，由宿主共同发布，不能为减少结构而合并账目所有者。

## 下一步全局新图设计约束

### 未来输出写权限的实施设计

完整未来图通过后、冻结前，将候选/恢复所有精确输出键的并集封存到原 Scope.stagedOutputs 与 registry.replacementOutputs，不新增键目录或绑定记录。准入只接受实际同 Kernel 的 Reserved Scope；同时检查原排他、实际 realm 和全部已占用绑定，不能仅检查公开可用服务。Staged/Held/Retiring 的外来占用均拒绝，旧实际闭包自己持有的绑定允许保留至原有序停止。所有分配完成后一次交换原索引，失败不留部分写权限；冲突报告真实阻塞操作编号。

Host 的计划完成须封闭后续新增输出权，否则只提前占一批键，拥有者仍能在 stage 时扩大未声明命名空间。Scope 增加单一 outputsSealed 许可模式，原 stagedOutputs 为唯一键集合；封存后 stage 只能使用其中键，候选失败恢复也保留原候选/恢复并集，真实释放仍沿原 removeClaims。低层未提供完整未来计划的原 Scope 保持动态 stage，不能用 Scope 生命周期状态推断这两种不同许可模式。预检与 stage 的 realm、绑定占用、其他操作排他和封存范围检查抽到同一私有 checkOutputs，删除 stage 重复实现；stage 原 Runtime/输入/发布组权限及同步四表发布不变。

实际绑定入账的 ServiceRegistry.stageErased 同样要检查尚未释放的封存 Scope 范围，覆盖使用发布组视图的原生服务适配器，不能只依赖 Runtime 创建路径。复用同一 checkOutputs；已 Released 的历史发布组及未封存的低层模式保持原行为，避免引用已移出的 Kernel，也不把输出限制误用于依赖读取。

验证用两个真实模块及两个实际旧树：第一操作预检后第二操作竞争相同未来键，必须在第二旧树停止前拒绝；取消第一后第二可重试并真实提交。另验外部 Staged/Held/Retiring 占用冻结前拒绝、放弃预检释放和低层动态行为。未来外部服务的读持有、模块来源与恢复输入完整性继续单独实施，不能把写键排他当作读权限或实际服务可用性。

### 全局服务求解的实施设计

把 Driver.order 的实际提供者索引、兼容性边和确定性拓扑排序移至 Core 私有 service_plan，并让 Driver 与宿主同时实际调用，删除 Driver 原算法。输入均为精确域的纯节点，父级和服务依赖共用边；同键多提供者、类型/minor/能力不符及环统一处理。普通配置使用 Pending 缺失策略，历史停止排序可关闭兼容性验证；替换使用 Reject，不能静默跳过未满足依赖。输出声明包括 optional，求解只证明声明可兼容，实际提供和消费者就绪仍由原 Core Prepared 证明，不从声明推出激活成功。

Core 私有 planningContext 从真实 Scope/Kernel 读取唯一注册表：只复制闭包外当前可用且非他事务占用的实际绑定（包含类型与元数据）及已有 realm 身份，不开放绑定或实例权限。旧闭包的实际绑定排除，防止旧服务冒充候选提供者；隔离候选/其他发布组不作为外部全局服务。宿主把所有拥有单元的候选/恢复规范计划合并，检查 realm 来源，再与真实外部绑定共同求解；不用每个 Driver 的局部排序代替全局图。

求解结果直接驱动本次创建单元的根顺序，子级仍由原父级 Context 和真实依赖门禁创建，不建立另一份运行索引或持久依赖图。预检两图、冻结前两图及实际构建阶段重验，外部可用性变化不能使用旧快照继续推进。新增纯节点的父链校验迁入同一排序器，删除 planConstruction 的独立父链遍历。全局求解不授予动态模块来源读意图，新增动态 DLL 工厂来源和多参与者/清理/投递故障矩阵仍需单独完成。

### 动态未来契约的实施设计

先补实际拥有者协议的缺失来源，再实现全局求解。IReplacementOwner.preflight 返回候选/恢复的纯值动态成员计划，仅描述没有规范工厂的成员及新增子节点：原成员 key、父 key、配置、realm、有效类型化依赖和输出，不携带 Runtime、实例、调度器或调用权限。已知工厂的契约由宿主从真实 Runtime 与附加依赖计算，不能由拥有者覆盖。Core 原 mergeDependencies/描述校验提取到实际共享实现，Core 入场与宿主未来契约同时复用，删除 instance.cpp 原函数体，不保留备用契约算法。

拥有者计划须完整覆盖原动态成员，拒绝重复、遗漏、外来父级及暗增顶层根。新增节点的 key 只在本拥有单元的预检返回值内有效；宿主为新增节点重分配事务内唯一 key 并转换父引用，再把规范后的完整 BuildPlan 交给 rebuild。因此不同拥有者可各自声明相同局部新 key，不引入全局插件编号或分配服务。候选/恢复各保留自己的形状，未换代旧成员对应继续由原 previous 提供；新增节点不伪造旧实例或配置执行记录。

纯契约直接附在已有 ReplacementConstruction 上，避免新增一套跨阶段图/输入索引。动态配置/realm 取拥有者明确描述的未来值，依赖按 Core 原精确 realm 合并，输出按真实描述规则验证；知道工厂的节点仍使用原实际来源。重建后从 Core Prepared 的真实工厂/输入计算同样契约逐项比较，全部真实子实例必须在已声明计划中，不再允许未描述额外子实例仅靠祖先关系蒙混提交。允许拥有者明确声明并创建新子节点，不能靠一律拒绝形状扩充缩小原需求。阶段弱许可、Module 预约和真实发布检查保持各自原所有权。

Core captureReplacementInput 有意不给临时子实例保留 factory，首轮把它当作实际契约来源导致全部常规换代失败。修正来源而不放宽该权限：ReplacementInput 追加实际实例的纯输出声明，依赖沿已有实际合并 dependencies，二者由 InstanceControl 同次捕获；Prepared 核验从这些真实值规范化比较，不取得或重放临时激活闭包。该纯值 SDK 结构与尚未发布的拥有者接口一起更新，宿主及 C++ 插件须重建，C ABI 不变。

此步骤交付的是全局新图的真实未来输入与兑现校验，不用旧输入冒充未来契约，也不声称已完成全局排序/外部提供者检查。随后全局求解须同时消费手动、配置、拥有者的这些规范计划，普通配置与替换共享实际算法且保留不同的缺失服务策略；全局图和故障矩阵未完成前不收口 M2c5。

全局规划须覆盖手动实例、全部配置参与者及动态拥有单元。已登记工厂的契约取自实际 Runtime；受影响范围外的可用服务取自同一 Core 注册表；动态拥有者现通过 ReplacementOwnerPreflight 提供未来隐式成员及新增节点的纯契约；后续求解必须使用这些实际规范计划，不能再从旧实例依赖猜测。规划只是校验输入，不能授予实例或模块权限；实际候选在发布前还必须对照契约重新核验。

在这些来源、拥有者协议、严格替换校验与普通配置 Pending 语义设计完整前，不新增另一个通用服务图实现，不用旧依赖快照假冒未来声明，不把当前 Driver 的局部排序当作完整全局图证明。后续若提取共同契约逻辑，必须同时接入实际调用者并删除原重复实现。

还有两项必须与新图一起设计的占用边界。未创建祖先没有 Core 实例可占用，两个不同模块的替换可能命中同一个 Driver 逻辑父路径；该互斥应归 Driver 的条目权限，按驱动身份与路径管理，不能伪造实例编号或用全进程路径锁。计划依赖但不换代的规范工厂也需要读意图：Core 保护规范 Runtime 来源，Module 保护实际模块代次，不能仅靠持有 Runtime 副本就假定不会换代或进入排空。

这些权限应组合在现有操作寿命内，取得失败撤销已取得部分，准备阶段完成可分配工作，发布段无业务回调；普通 Session 的冲突检查须在接受目标前生效。实际祖先、逻辑祖先、借用工厂与动态契约各有不同来源，先完成来源与释放协议，再扩充状态字段和接口。当前结构收敛不宣称这些剩余并发权限已经实现。

取消/晚到场景还需要阶段权限边界。目前拥有者直接取得整个 ReplacementScope；回执序号可以阻止旧回执推进状态，却不能单凭序号撤销拥有者保留的 stage 能力。后续拥有者应取得绑定当次发布组的构建许可，丢弃候选即撤销该许可，恢复必须取得新许可；旧许可不能自动取得后来恢复组的权限。许可不应让成功历史或拥有者门面长期强持 Kernel、旧工厂或新旧发布组。

参与 Session 关闭与 Kernel 关闭也须区分：需要明确关闭信号怎样取消仍在等待的拥有者任务、怎样等待真实清理及报告保留资源；不能仅在下一次提交时轮询 closing，也不能把任务完成当作资源已静止。阶段许可、取消/关闭信号与动态契约应在同一拥有者协议设计中核对，再修改该尚未发布的宿主接口，避免连续增加布尔参数和零散补丁。

### 构建阶段许可的实施边界

先实施最小权限替换：IReplacementOwner.rebuild 接收 ReplacementBuilder，替代整套 Scope。Builder 只公开 stage，不公开 discard、release 或取得新阶段的方法；内部只保存 Scope 控制块与当次 PublicationControl 的弱引用。候选和恢复各取得自己的许可，准备/清理/失败/发布后关闭，旧许可不能跟随 Scope 自动切换到新组。

Core 共用一次发布组初始化逻辑，保留低层 ReplacementScope.stage 的现有调用契约。根创建在入口与 claims 发布前核对许可，并捕获具体 PublicationGroup 传给 Kernel，避免调度器重入后读到另一个当前组。Context.inject 沿原组视图继承权限，亦在实际声明准入中核对组身份。默认构建与宿主拥有者使用相同阶段许可，不增加一个允许绕过的构建入口。

本次不扩充动态契约或关闭信号接口；它们继续列为阶段未完成项。验证先重现旧 Scope 在恢复阶段仍可 stage 的真实两后端场景，再验证旧/新组、空组丢弃、错误线程、准备/发布后关闭及弱许可不延长工厂寿命。保留低层 Scope.stage 的兼容性检查，并复用全部实际拥有者/恢复回归。

## 验证与删除审查

### Driver 逻辑重建占用

目标是完整事务所需的实际权限，不是第二份运行索引。Core 继续占用真实实例、输出和定义；Driver 私有 DriverReplacementClaim 占用本驱动将重建的规范路径及本次变更的模块别名。无实例的祖先也取得路径占用，按斜杠边界判祖先/后代，不能把 p 和 peer 当成同一子树。路径去掉被祖先覆盖的冗余项；真实 Module/Core 操作编号仅用于来源、冲突和原释放事件，不伪造实例编号。

1. 取得占用须传实际 Driver、Scope、新目录和目标，复用 inspectReconstruction 从真实来源重新校验并派生路径，不能拿调用方路径集合授予权限。每个 Driver 保存弱持有的操作占用表；凭据强持原控制块及无回调的目标值，不复制 Runtime/实例账目。节点在准备段预分配，最后纯重验并 merge 单个节点，不能用旧整表覆盖重入取得的其他占用。
2. 宿主在拥有者预检回调前取得全部 Driver 占用；后续参与者失败、预检放弃和启动失败均撤销已取得部分。成功/恢复发布后，先在无回调段解除 Driver 占用，再沿原 Core release 发出真正释放通知；失败保留占用，Kernel 真实释放后不能继续以旧凭据阻塞或提交。
3. 普通目标准入复用 previewChanges 的 desiredChanged 与模块定位差异，拒绝占用子树的属性/形状/启停/定位变化，保留无关目标编辑。普通执行和后台恢复共用 pathAccess/entryAccess；没有记录的原接受条目也可返回 Pending NoOp 等待原 whenReplacementReleased，不提前建立执行记录，也不抢先挂载祖先。直接 Add/Recreate 等入口同样检查路径权限。
4. 最终 Driver 准备须重验同驱动、同真实 Scope 操作、仍有效的凭据；准备窗口保留来源并在 ready 再验。低层无占用的既有调用继续可用，但不能绕过已存在的占用。正常 Module 预约和 Driver 占用均在 Core 通知之前解除，Session 关闭持有仍待操作结算后释放。

占用簿与纯差异门禁放入 ConfigKernel 私有 replacement_claim 文件，Driver 只负责从真实重建检查派生权限。低层调用未提供长事务凭据时，由实际 Prepared Scope/旧记录在准备窗口取得短期凭据；同样重验占用簿身份，不能用缺省参数跳过已有占用。凭据析构只解除自身节点，不触发回调；不再维护另一份 released 状态，真实节点身份和 Core 原释放 Task 决定有效性。

验证使用两个真实 C ABI 模块（主模块可切 Qt 后端）：父配置已停止、两个业务子项没有实例时，第一操作已取得占用而未停止，重叠第二操作必须在冻结前拒绝；独立路径允许并行，目录与保存目标不能互相覆盖。测试 peer 复用现有业务夹具，以同一宏提供查询/业务插件标识，删除重复硬编码；不伪造工厂来源或另建仅用于通过检查的模块实现。组件检查占用释放/重取、外驱动/外 Scope、普通目标 CAS 前拒绝、未创建条目 Pending 和直接执行门禁。

另已识别预检回调关闭 Session 时的资源释放顺序仍需补证：会话持有取得时间与预检失败撤销必须配合，不能先启动 Driver 关闭再解除 Reserved Core。此项与规范工厂读意图、全局新图一起保持 M2c5 未完成，不因逻辑占用增量提前收口。

### 规范工厂的 Core 读意图

独立路径的真实两模块测试暴露：新根共用未换代父工厂时，旧 claimStage 把它当作新增顶层 Runtime 全局排他，两个操作无法并行。不能仅删除排他检查；先补上规范定义的读意图。

复用原 registry.replacements 和 Scope 控制块，在 Scope 保存实际借用的规范 RuntimeId 集合，不另建读者索引或运行图。宿主在拥有者回调前，把候选/恢复构造输入中的已登记工厂提交同 Kernel 的 Core 私有借用入口；自身换代定义已有排他，不重复登记。入口重验真实 Scope、当前规范工厂和其他排他，节点预分配后纯重验并 merge。多 Scope 可共享读意图；任何以该 Runtime 为换代目标的预约须先查现有 Scope 的读意图，失败保留到实际释放。

只有已持读意图的新根可跳过旧顶层 Runtime 排他，其输出、真实实例、阶段组和发布门禁仍沿原机制；低层未借用入口保留旧行为，且不能反过来取得已有读者的定义排他。Scope 正常释放和 Kernel 真实清理沿原 removeClaims 解除读意图。此项只保护同 Kernel 的规范定义；Module 代次的生命周期/预约读意图仍须独立接入，不能用 Runtime 强引用或本次并行测试宣称它已完成。

原闭包成员本身已持有定义读权限。用 readsDefinition 共用原始来源和新增借用集合，预约与低层新根准入使用同一判断；删除重复分支，不给已有原成员再存重复读节点。借用入口仍校验全部传入规范工厂，不能因已有权限跳过来源检查。补低层空作用域试图把另一 Scope 原有子工厂当作全局排他新根的负向场景。

### 计划工厂的 Module 代次读意图（实施设计）

问题已由真实 native/Qt 配置树复现：未创建的同级业务工厂进入重建计划后，低层仍能预约其模块；Core 规范定义读权限不能保护 Module 生命周期。扩展已有 ReplacementReservationControl.borrowed 与 ModuleCatalog.readers，不增加第二套读者目录。宿主在拥有者回调前，将候选及恢复计划的真实 Runtime 交给 Module 私有 ReplacementAccess；Core 先验证同 Kernel 的工厂权限，Module 再从唯一 runtimeOrigins 查实际代次，而不是采信调用方提供的来源快照。

入口只接受同操作的 Reserved Core Scope 和仍在目录中的真实预约，持目录锁及逐代锁检查已有排他、准入、健康和资源接受状态。候选使用决定 required，恢复使用决定 original，防止候选专有代次失败后错误阻止旧代恢复；恢复授权沿原机制重置 required。先在副本完成全部检查和节点分配，再原子交换原读者账目，失败不留下部分占用。自身换代模块仍由原排他预约保护；内置工厂没有 Module 来源，保持原行为。释放、保留失败、关闭、drain 和最终提交继续使用原账目。低层预约冲突应报告实际阻塞操作编号。

验证先保留修复前两后端 0/2 的日志，再检查计划工厂的预约/关闭拒绝、独立路径并行不被扩大阻塞，以及现有候选失败恢复和释放后的再次换代。此增量不替代 Session 预检撤销顺序、全局依赖图或 M2c5 最终矩阵。

### Session 关闭的持有与恢复协议

#### 预检关闭与撤销顺序（实施设计）

当前持有在拥有者预检之后取得，回调 close 可使 Driver 在 Core 仍为 Reserved 时开始停止，产生本可避免的关闭失败。会话持有必须前移到实际 Session/Driver 配对及原修订核验之后、取得 Core 预约之前，覆盖后续 schema/availability/拥有者等可重入边界；不新增关闭状态副本。回调关闭后预检拒绝，不能开始破坏性替换。

预检退出由宿主显式撤销，不能依赖 Execution 默认成员析构的逆序：先解除无需回调的 Driver/Module 权限，再释放 Core 原占用并完成原恢复通知，最后放弃 Session 持有，允许原 Driver/Store 关闭。Core 在预检只允许 Reserved，若外部关闭或投递失败使其无法释放，不得先解除 Module 权限并宣称撤销成功；需从真实 Core 状态区分已经释放与仍保留，保留实际执行所有者及诊断，Session 自身关闭仍沿原门禁报告实际结果。处理开始排队失败时复用同一撤销协议，避免再保留一套相同释放分支。

Core 私有组合 SPI 在原 release 的准入全部通过后、removeClaims/通知之前执行宿主提供的纯解锁动作。公开 Scope.release 保持原入口与行为，不向插件开放回调参数，也不让 Core 依赖 Module/Loader。已 Released 的真实作用域同样允许解除外围权限；Failed/阻塞而未释放时不调用解锁动作。宿主 releaseClaims 统一提供 Module.reset/DriverClaims.clear，准备失败或投递失败通过 abortPreparation 汇合；释放失败保留真实 Execution 并观察 Kernel 最终关闭，错误链报告清理失败，不能仅丢弃门面掩盖残留。Session 持有最后释放，避免提前触发 Driver.stop。

实施前先用真实 native/Qt 旧业务、两个配置会话及手动实例复现拥有者预检 close；普通发起关闭不足以复现，回调须推进真实调度器/原生嵌套事件循环，覆盖正常返回与抛出，再补更早的 availability 回调。预期 begin 拒绝且没有候选构建，关闭会话成功保存原目标，另一会话及手动实例保持原实例/旧代，预约撤销后可再次取得；随后验证早期 schema 回调、部分会话取得失败和排队失败等交错。保持 M2c5 进行中，不能以常规预检撤销代替整个 Kernel 非静止失败保留矩阵。

Session 关闭只拥有自己的 Driver/Store，不能代替宿主关闭整个 Kernel，也不能遗弃同一替换中的手动实例或其他会话。采用 Loader 私有 SessionReplacementHold：宿主在实际会话/驱动配对及原修订核验后、Core 预约前取得持有凭据，Session 仅计在途持有数量，不复制模块或实例索引。凭据同时观察操作结算任务；结算不代表资源静止，释放持有后仍由 Driver 原 stop 和 Store 原保存证明关闭结果。放弃启动释放凭据，投递失败沿原 SessionDelivery 失败报告，不无限等待操作正常返回。

close 先设置原 closing、发出一次私有 closingStarted 通知并封闭全部公开业务；有持有时，不启动 Coordinator/Store 关闭。没有持有时，Coordinator 按原语义立即封闭自己的接受门禁，Store 仍等待业务访问栈返回。宿主收到通知沿同一取消路径丢弃候选并恢复完整旧闭包，包含手动实例及其他会话。关闭中的 Session 仅凭属于自己的有效持有凭据，允许 Preserve 模式的元数据准备；Advance、新目标和普通业务仍拒绝。检查来源、修订、原目录和准备身份不放宽；准备窗口保留凭据来源并在 ready 重验，原持有释放即失效。Driver/Coordinator/Store 此时尚未关闭，因此不绕过它们的关闭门禁。

所有持有释放后，Session 启动原 Coordinator 关闭；Store 最终保存还须等待业务栈退出，再汇合真实回执。恢复失败时操作仍保留真实 Core/Module 资源并封闭创建，但释放关闭持有，让 Driver 原清理检查报告真实结果；不通过持有让会话永远等待一个已终结的操作。整个 Kernel 同时关闭时，由原 Kernel 清理结果优先结算，不向关闭 Kernel 恢复。拥有者回执与关闭通知均经 owner 串行门禁，最终候选发布还必须检查真实 Session closing，不能靠通知排队顺序授权。

实施时将原 Session.close 内重复的 Coordinator 启动逻辑移到 advanceClose 唯一入口，并复用一次业务可用性检查；不另建一套 Session 生命周期。验证先复现拥有者悬挂的真实两后端关闭，再检查会话实际保存/关闭、手动实例旧代恢复、晚到候选拒绝和模块预约解除，随后补启动前、停止中及提交回调关闭交错。

最后的可用性回调也可能在旧代恢复提交中请求关闭。全局发布前同步读取原会话关闭信号并登记取消，再依原候选/恢复权限判断，不能仅在候选分支检查，否则恢复已发布但报告会漏记关闭取消。无配置参与者时不创建无人消费的会话结算观察器。

### Kernel 关闭完成与悬挂拥有者

Kernel 已有唯一 closed_ 清理结果；宿主通过 Core 私有只读适配取得其 Task，不发起关闭、不新增关闭状态或信号。观察器跨构建阶段有效，仅弱持宿主控制块；收到实际关闭结果后经原 owner 调度门禁结算。quiescent 为真才释放模块意图与执行输入，失败则按原失败保留协议处理；关闭中不尝试向同一 Kernel 恢复旧实例。正常提交先完成时，观察器的终态检查忽略后续关闭。

拥有者可能永远不兑现重建 Task，因此其完成观察器不能捕获带 Runtime 的整份计划。改为只捕获稳定的单元索引，阶段序号核对后从唯一 Execution 读取当前计划；默认构建沿同一路径接纳结果。关闭监听先于 start 投递安装，先保存调度器，再处理监听同步重入，避免结算释放 Execution 后继续解引用。Session 单独关闭仍需独立设计，不以 Kernel 清理完成代替参与者关闭协议。

验证用实际 native/Qt 拥有者挂起候选，显式关闭 Kernel 并等待真实清理结果，操作必须完成、阶段许可失效、模块意图解除，晚到拥有者回执不能改变历史结果。

关闭开始后，普通阶段回执可能先于关闭完成通知到达。启动、错误处理和阶段观察器须直接读取同一 Kernel 的原 closing_，关闭中停止普通推进，等待独立关闭结果；不能先进入恢复或终结为保留失败，让真正静止的结果失去结算机会。不增加宿主 closing 副本；补启动前与停止期间的真实关闭交错。

本轮不增加模拟实现结构的测试，复用真实 C ABI/Qt 操作、动态子树、取消、失败恢复及配置共同提交场景；核对公开 SDK 变更范围及 C ABI 兼容性。结构收敛后运行 Release/ASan 相关回归、GCC 配置组件、格式/源码及实际 ASan 对象检查。
