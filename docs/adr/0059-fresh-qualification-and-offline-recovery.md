# ADR-0059：重新采证与离线更新恢复

日期：2026-11-23。状态：P6-3 已以56c47c1完成审查、归档、提交同步与clean；P6-2 已由 `37d1cf4878966d3d007572fb29b04160257a4d9a` 提交、同步并核 clean。范围仍为内部 Windows x64 技术预览。

## 问题与现有边界

用户确认19份历史资格原件没有备份，要求重新采证。旧文件路径、预期SHA及缺失事实继续保留；新报告不能冒充这些原件。真实旧包 `0.1.5-preview.2`（ZIP SHA `d236f5965bccf124eabde8fa0f1539fd910e2eff33a432affbea0174d18c7168`）和本轮真实接受的13文件业务数据可用。P6-3需要一个经过新资格与审查的新包来实测旧包至新包的更新，不能将同包复制称为升级。

运行时仍由 ModuleManager、Session、Store拥有批准检查、状态迁移、冲突及保存；Qt模块继续驻留。部署脚本只拥有离线文件部署、明确的定位映射、进程退出检查和应用/数据选择记录，不引入第二套运行状态机或跨进程草稿承诺。

## 新资格及受信输入

1. 在独立新目录完整配置、构建 Release、Debug、RelWithDebInfo/ASan 三个既有固定profile，原公开27项各实际执行一次完整采证。沿用现有采证器的实际选择、串行执行、物理/回放/非法轨迹/缩减证据、source/producer/dependency和Ninja no-work检查，不以窄Release观察替代三profile资格。
2. 构建期间冻结C++、CMake、资源、依赖、旧批准源及原采证器；无构建依赖的离线Python工具可并行实现。开始公开采证前另明确冻结全部 `source_inputs()`，直至候选导出结束，包括新Python/PowerShell输入。采证器真实拒绝的不一致应修正并新建campaign，不改原报告。
3. 候选只写独立build输出，必须独立审查后才允许按同字节采纳到固定版本路径 `qualification/native-business-p6-3-20261123.json`。原 `qualification/native-business.json`（SHA `6c0c5324e0e064667c79ae10ff9cf2d48754cbffd49f376d338d4e8cd91786ec`）保持不变。采纳提交明确固定新路径及SHA；不提供cache/env/CLI批准源选择，不按文件存在自动采用候选。采证器不得覆盖任一受信文件。
4. 每profile仍只含四条Native身份/SHA；三个profile的12条不得合并编入一宿主。新产品在采纳前对未批准新字节的保守拒绝是预期行为，不能声称产品正向全部通过。采纳后只重建名单消费者，再逐项核生产模块/manifest/依赖未变，运行真实产品正向和支持矩阵。
5. 新包采用独立、严格的新采证打包基线，绑定实际原件、独立审查、生成名单、消费者及Release产物。旧P5/Unicode宿主19件门禁留作历史路径，不回填、跳过或以新SHA重命名。打包只复制已资格的准确字节；新清单不再声称新包与旧P5全同。包版本至少为 `0.1.5-preview.3`，旧包保留用于恢复。

## 离线部署模型

应用版本目录并列且部署后不覆盖；每次迁移完整复制已关闭的实际数据树，并保留原树、备份、未知store及PIN。选中新模块仅添加到不可覆盖的hash目录。不能删除无法证明闲置的模块或目录，也不能覆盖仍加载的DLL。更新操作必须确认所管理旧产品已经正常退出；外部未知使用无法证明安全时拒绝推进。

唯一激活入口是包含应用路径、数据路径、准确包锚和前驱摘要的一份应用/数据tuple文件。不能分别更新两个指针。部署journal只记录文件阶段与不可变回执；文件使用独占新建及同目录原子替换，提交前再核前驱摘要。单次部署持有自己的租约，失败/中断保留部分目录及原件，恢复只能回到已接受的旧tuple，或继续提交已完整验证的新tuple。

已有session在新宿主启动前就会校验旧hash，不能先用新宿主打开未映射配置。离线工具仅在未激活的数据克隆内执行有界、无状态的既有JSON format1定位映射：明确绑定旧/新包、模块ID、版本、schema、旧/新DLL及manifest摘要；同版本号本身不构成批准。仅替换定位字段和增加对应store文件，保留所有其他配置与未知数据。随后由新宿主原Session/Store完成解析、运行、显式Save和正常退出，实际外部验证通过才激活新tuple。部署工具不仿写runtime revision或迁移插件内存。

用户配置偏好由原产品拥有；业务 `--file` 不会重定向这些偏好，验收将单独记录其真实位置和变化，不擅自覆盖或回滚个人KnownFolder。

## 验证与出口

纯文件测试覆盖严格包/映射校验、路径与重解析点拒绝、完整备份、未知store/PIN保留、前驱CAS、并发租约、每个部署阶段的故障与中断、重复恢复及错误输入。实际验收使用准确旧包和新包、真实接受数据、普通QA客体桌面与既有UI脚本，检查迁移后的实际模块/文档、显式保存、正常退出及重新打开，并实测故障恢复旧版本和数据。

阶段审查须核职责、资源所有权、删除被替代路径、旧/新证据边界、真实退出和包/数据字节。完成精确提交同步clean后P6-3才结束；P6-4分层CI与P6-5最终准确包人工体验另按顺序执行，不借用旧包人工回执。
